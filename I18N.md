# Internationalization architecture

This is the spec for how additional languages get added to this site. The
technical foundation described here is already built and live (as of
September 2026) with English as the only locale. Read this before adding a
second language, whether that's a person or the nightly maintenance routine
doing it.

## URL structure

**English stays exactly where it is, forever: unprefixed at the site root**
(`/holafly/`, `/compare/holafly-vs-airalo/`, etc.). It has real Google
ranking history. Do not move it, alias it, or generate an `/en/` copy of it.

**Every additional locale lives under its own path prefix**:
`/de/holafly/`, `/es/holafly/`, `/de/compare/holafly-vs-airalo/`, and so on.
This is the standard, unambiguous pattern (subdirectories, not subdomains or
a `?lang=` query param) and it's what the hreflang/canonical machinery below
assumes.

## `src/_data/locales.json`

The single registry of enabled languages. One entry per locale:

```json
{
  "code": "de",
  "hreflang": "de",
  "label": "Deutsch",
  "ogLocale": "de_DE",
  "prefix": "de",
  "default": false
}
```

Exactly one entry has `"default": true` (English). Adding a locale means
adding one entry here — nothing else reads a hardcoded language list.

## How a page declares itself translatable

Any page that has (or will have) a same-content counterpart in another
locale sets two things in its own `eleventyComputed`:

- `translationKey` — a stable id shared across every language version of
  that *same* page. Providers use `"provider:<providerKey>"`
  (e.g. `provider:holafly`); comparisons use `"compare:<slug>"`. Pick this
  key from the content's identity, not its URL, so it doesn't change if a
  URL ever does.
- `locale` — that page's own language code, matching a `locales.json` entry.

That's the entire contract. A `.eleventy.js` collection (`i18nMap`) walks
every page at build time, groups them by `translationKey`, and produces
`{ translationKey: "provider:holafly", locales: { en: "/holafly/",
de: "/de/holafly/" } }`. `meta.njk` and all three sitemap files read that
map (via the `i18nAlternates` filter) to emit `<link rel="alternate"
hreflang="...">` in `<head>` and `<xhtml:link>` in the XML sitemaps,
automatically, for every page that has 2+ locales.

**This means: the moment a German counterpart of `/holafly/` exists and
declares `translationKey: "provider:holafly"`, the *existing* English page
starts emitting a correct hreflang pair to it on its own.** Nothing on the
English side needs editing. A `translationKey` with only one locale (today's
reality, site-wide) produces no hreflang output — correct, since a single
page isn't an "alternate language" of anything yet.

`x-default` is always included automatically and always points at the
default locale (English).

## Canonical URLs

Untouched and correct by construction: `canonical` is computed per-page from
`page.url`, so a translated page always self-canonicalizes to its own URL.
**Never** point a translated page's canonical back at the English version —
that would tell Google to ignore the translation entirely.

## Adding a new locale: the concrete steps

1. Add the entry to `src/_data/locales.json`.
2. Create a locale directory that mirrors the existing pattern, e.g.
   `src/de/provider.njk`: same `pagination`/`permalink` shape as
   `src/provider.njk` but `permalink: "/de/{{ providerEntry[0] }}/"`,
   `eleventyComputed.locale: "de"`, and `translationKey` set the same way
   English does. It still reads `provider` straight from `codes.json` —
   **codes, discounts, dates, and URLs are language-neutral data and are
   never translated or duplicated**, only the prose around them is.
3. Long-form article prose (the equivalent of
   `src/_includes/content/holafly.njk`) is real, fact-checked writing, not
   short UI strings — it does not belong in a translation-key JSON file.
   Give it its own file per locale: `src/_includes/content/de/holafly.njk`.
   Translate meaning, not word-for-word; keep every specific claim
   (numbers, policies, dates) identical to the verified English source,
   translated faithfully, never re-verified from scratch in the target
   language unless something is genuinely locale-specific (e.g. a
   provider's plan lineup differs by country).
4. Site chrome (nav labels, footer, button text, badges, disclosure
   boilerplate) is wired through `src/_data/i18n.json` (`{ "en": {
   "nav.findACode": "Find a Code", ... }, "de": { "nav.findACode": "Code
   finden", ... } }`) plus the `t` filter (`'header.findACode' | t(locale)`
   in a template), which looks up `i18n[locale][key]` and falls back to
   English if a key is missing. `header.njk`/`footer.njk` are shared across
   every locale and already use it — a brand-new locale's chrome strings
   just need adding to `i18n.json`, not a new header/footer file.
5. Provider-specific discount/description text (the natural-language
   fields inside `codes.json`, e.g. a code's `discount` or a provider's
   `description`) is overlaid per locale in `src/_data/codesDe.json` (one
   file per locale, e.g. `codesEs.json` for Spanish), keyed by provider
   then by the exact code string. `codes.json` itself is never edited for
   this — it stays English-only, permanently. Every template that renders
   one of these fields (`src/de/provider.njk`, `src/de/compare.njk`, and
   any content file that quotes a discount inline) looks up the overlay
   first and falls back to the English value when no override exists yet,
   so a partially-translated provider never renders blank.
6. Comparison pages follow the same shape as providers:
   `src/de/compare.njk` (mirrors `src/compare.njk`, but
   `permalink: "/de/compare/{{ cmp.slug }}/"`, `locale: "de"`,
   `translationKey: "compare:{{ cmp.slug }}"`) paired with
   `src/_data/deCompareEntries.js`, which scans
   `src/_includes/content/de/compare/` the same way
   `src/_data/deProviderEntries.js` scans `content/de/` for providers: a
   pair gets a `/de/compare/<slug>/` page the moment
   `src/_includes/content/de/compare/<slug>.njk` exists, no template edit
   needed. **A new English comparison page and its German translation
   should ship in the same run/commit whenever possible** — translating a
   growing backlog later is real, repeated work; writing both at once
   while the English content is still fresh in context is not.
7. Every internal link inside a translated page or its content file
   (provider cross-links, "full code list" links, breadcrumbs, the header
   logo) must resolve through `collections.i18nMap | i18nAlternates(...)`
   (falling back to the English URL, never a bare guess) rather than being
   hardcoded — see "Real bug this caused" below.
8. Build, confirm the new URLs render, confirm `curl` on an existing
   English page now shows the new hreflang pair in `<head>`, confirm the
   sitemap picks it up, then commit.

### Real bug this caused (read before writing a new locale template)

The header logo, the nav "Find a Code" CTA, and the German provider
breadcrumb all originally hardcoded `href="/"` — fine for English, wrong
for every other locale, since it silently sent a German-page reader back to
the *English* homepage on every click. Fixed once, generically, with a
`homeUrl` filter in `.eleventy.js` (`{{ locale | homeUrl }}` -> `/` for the
default locale, `/de/` for a prefixed one, driven by `locales.json`, not a
hardcoded string). **Any new template — a new locale's provider/compare
page, or a shared include — must use `{{ locale | homeUrl }}` for its
"home" link, never a literal `"/"`.** The same class of bug applies to any
other link that looks locale-neutral but isn't: prefer
`collections.i18nMap | i18nAlternates(...)` or `homeUrl` over a literal
path anywhere a locale other than English might render the template.

## Rules that must never get violated

- Never fabricate or approximate a discount, date, or verification claim in
  a translated page. Same honesty policy as English, in every language.
- Never point a translated page's canonical at anything but itself.
- Never remove or renumber `locales.json` entries that are already live —
  that would break every hreflang pair pointing at them site-wide.
- Never translate a page without also giving it the matching
  `translationKey`/`locale` pair — an untranslated-looking page with no
  hreflang linking it to English is invisible to this whole system.
